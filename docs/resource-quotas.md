# Aggregate resource quotas

Open a project's **Capacity and quotas** card. All organization members can inspect project allocations; platform administrators can edit project, current-organization and host ceilings. Blank limits preserve unlimited behavior. Host memory/CPU ceilings describe the Docker host's allocatable total; configured headroom is subtracted before admitting tenant allocations. Set these from the actual Docker host/VM capacity, not the browser computer's memory.

A single database transaction lock serializes reservation checks across all projects in this Ferrix installation. Create, configuration changes, manual deploy, rollback, backup restore and GitHub auto-deploy use the same checks. API keys obey their user's permissions and project scope. A blocked GitHub push remains pending until capacity is available. Queued and running jobs reserve deployment/build slots; completed jobs release them automatically.

RAM/CPU accounting reserves the maximum of configured, active and pending snapshots for each service. Stateless redeploys also reserve overlapping old/new containers during readiness checks. Persistent Applications and workers stop first and reserve the larger snapshot instead. PostgreSQL/MariaDB/Redis retain their existing 512 MiB/one-core defaults; MongoDB reserves its existing 1 GiB/one-core default. Build processes need additional host headroom; service limits are runtime container limits, not BuildKit process limits. Stopped services retain their resource allocation and volume data.

Introducing or reducing a quota never stops or deletes existing services. A scope already over its ceiling may keep or reduce allocation, but cannot increase the exhausted resource. A rollback to a larger saved runtime also needs available capacity. Deleting services releases runtime/count allocation; retained data volumes remain in the storage ledger once sampled.

Storage is **advisory**, because Docker local volumes do not implement a portable hard byte quota. The background collector samples managed local volumes every two minutes where the Docker API supplies usage data. Unsupported, failed or older-than-five-minute samples are unavailable rather than zero. Storage reports may be partial. Notifications report threshold transitions and recovery without stopping applications. Volume imports/restores obey service/RAM/CPU/count quotas, but archive expansion is bounded separately by backup safety limits; do not treat an advisory storage threshold as a filesystem guarantee. Monitor free host disk space and provision real filesystem/project quotas externally when hard byte isolation is required.

API: `GET/POST /api/v1/projects/{id}/quota`, `GET/POST /api/v1/organizations/quota`, and platform-admin-only `GET/POST /api/v1/admin/capacity`. POST fields are nullable `memory_mib`, `cpu_centi` (100 = one core), `services`, `databases`, `deployments`, `builds`, `storage_bytes`, and host-only `reserved_memory_mib`/`reserved_cpu_centi`. Quota writes require a platform administrator browser session; API keys cannot raise ceilings. HTTP 409 explains which resource prevented an admission.
