# Private ingress, LAN and Cloudflare Tunnel

Use `FERRIX_AUTO_DOMAIN=private`, `FERRIX_INGRESS_IP=<Caddy LAN IP>`, `FERRIX_DOMAIN_SUFFIX=home.arpa`, `FERRIX_WEBSITE_HTTPS=true`, `FERRIX_WEBSITE_HTTPS_PORT=443` and the existing ingress network. A public IPv4 and inbound Internet ports are not required. Set `FERRIX_DOMAIN` to the dashboard's canonical hostname. In production, use `deploy/Caddyfile.private` in place of the public Caddyfile. It issues internal certificates, including the dashboard certificate. The public VPS/sslip.io configuration remains available unchanged.

Configure internal DNS to resolve automatic `app-<id>.home.arpa` names to the ingress IP. For friendly application names, add a **LAN** mapping in Domains, publish its A/AAAA and `_ferrix-challenge.<hostname>` TXT ownership record in your internal resolver, then check it. Split DNS may resolve the same public hostname internally to Caddy and externally to Cloudflare, but the Ferrix resolver must see the records appropriate to the mapping being checked. A tunnel and LAN mapping can use different hostnames for unambiguous checks. Trust Caddy's public root CA certificate on clients and in the Ferrix runtime trust store; never distribute its private key. Nonstandard LAN ports are included in generated links.

For public access, create a remotely managed Cloudflare Tunnel and published application hostname in Cloudflare. Add a **Cloudflare Tunnel** mapping in Ferrix, publish the TXT proof, then use **Review tunnel rule** for the exact origin settings. You can enter those settings into Cloudflare or merge the generated JSON rule into a locally managed cloudflared configuration. Preserve unrelated routes and retain your final catch-all rule. Ferrix does not store Cloudflare account tokens, connector credentials or CA private keys. Keep connector credentials private and scoped to that tunnel.

`FERRIX_TUNNEL_ORIGIN` is the origin address as seen by cloudflared (default `https://proxy:443` on the Compose network). For another host/port, set it explicitly. HTTPS rules include `httpHostHeader`, `originServerName`, and `caPool`. Mount the public Caddy CA certificate at `FERRIX_TUNNEL_CA_POOL` inside cloudflared; keep TLS verification enabled. An explicit HTTP origin is supported only where the operator intentionally chooses trusted local transport. Public browser traffic still uses Cloudflare HTTPS. For a local config run `cloudflared tunnel ingress validate` and `cloudflared tunnel ingress rule https://app.example.com` before switching traffic. Ferrix exports one mapping at a time and never rewrites the tunnel or its sibling routes.

Domain ownership/DNS, certificate validation and HTTP reachability are separate states. Tunnel DNS may be proxied and need not match the LAN IP. Public probes require ownership proof and public DNS destinations, have bounded timeouts and do not follow redirects. Connector health is **not queried**; a reachable public HTTPS endpoint is not proof that a particular connector is healthy. Check connector state in Cloudflare. A running Docker container alone never marks a domain reachable. Loopback URLs are server-only diagnostics, not client-facing website URLs.

Choose a verified mapping as the preferred website URL. Redeploy preserves mappings, and deleting one falls back to the automatic URL without removing other routes. This preference changes Ferrix's Open website link; applications that generate absolute redirects/assets must also set their own external base URL in their runtime environment.

Dashboard canonical origin is separate: `FERRIX_AUTH_ORIGIN` must exactly match the browser HTTPS origin (production Compose derives it from `FERRIX_DOMAIN`). Change the operator configuration and restart Ferrix when changing the dashboard hostname. Sign in again on the new hostname: host-only cookies do not transfer between hosts, and cross-origin mutations remain rejected. Update GitHub webhook URLs to the new origin. Application domain edits never change dashboard authentication settings.

References: [Cloudflare ingress configuration](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/).

For a containerized Ferrix API, mount only Caddy's **public** root certificate read-only into the API container and set `FERRIX_INGRESS_CA_CERT` to that file path. The Domains probes add this CA to their normal trust roots; hostname/certificate verification remains enabled. Do not mount Caddy's private keys or its entire data volume into Ferrix or cloudflared. For example, an operator Compose override can mount `./caddy-root.crt:/etc/ferrix/caddy-root.crt:ro` on `ferrix` and set `FERRIX_INGRESS_CA_CERT=/etc/ferrix/caddy-root.crt`. The cloudflared container needs its own read-only mount matching `caPool`.

An HTTP tunnel origin requires an explicit HTTP-serving Caddy site, not Caddy's automatic HTTP-to-HTTPS redirect listener. The provided private Caddyfile uses HTTPS origins by default. For trusted local HTTP transport, adapt `deploy/Caddyfile.local` for the private origin listener and keep the dashboard on its canonical HTTPS hostname.
