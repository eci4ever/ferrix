# Retained monitoring and logs

Open **Monitoring history** in a service's Monitoring tab, or on the platform administrator's host Monitoring page. Choose a time range, inspect CPU/RAM, network or disk I/O, then correlate vertical markers and the event table with deployment/image IDs, health and restart changes. Service history also searches retained logs server-side across deployments. Each log record separates Docker's emitted timestamp from Ferrix's collection time; embedded application timestamps remain unchanged in the message. Older matching logs use cursor pagination.

Collection runs in the API background without a browser. Default sampling is 30 seconds, with a bounded batch of 32 services and four concurrent probes. Busy/slow hosts or larger inventories may have longer gaps; sampling is best effort rather than a real-time guarantee. Docker statistics and OS namespace data are retained in PostgreSQL and survive Ferrix restarts. Final bounded log tails are captured before obsolete deployment containers are removed. Missing data, failed probes, resets, collection limits and retention gaps are not displayed as zero/healthy measurements. Host values retain their existing API OS namespace scope; they do not claim to describe a physical host or Docker VM when Ferrix runs in another namespace.

Platform administrators configure sample interval (10–300 seconds), metric/log retention (1–30 days), a shared logical-payload cap (16–1024 MiB), older-data bucket size/age, sustained CPU/RAM/disk thresholds and restart rate thresholds. Defaults retain three days under a 128 MiB logical-payload cap. Older buckets preserve boundary and peak observations plus error/transition markers. The cap may remove older markers too. Samples/logs are pruned after each collection cycle; up to one bounded cycle may temporarily exceed the configured payload target. Indexes, WAL, dead tuples and physical PostgreSQL files are additional storage; normal autovacuum and database operations remain necessary. Query responses cap charts at the newest 1000 points and log pages at 200 records; narrow the range or paginate to inspect more.

CPU/RAM alerts reuse Ferrix's notification inbox with sustained thresholds, hysteresis, durable deduplication and recovery messages. Host disk pressure and repeated service restarts use the same inbox. Missing samples reset sustained observation windows and do not imply recovery. Docker log rotation, unsupported log drivers, bursts above the collection budget and unavailable telemetry can create gaps. Each collection reads at most 5000 log lines and 256 KiB per service; retained messages cap at 16 KiB and report truncation. Collection does not parse or store container environment/configuration secrets. **Application-emitted logs may contain sensitive values**: avoid logging credentials and configure appropriate retention/access for your organization.

Historical service routes enforce current organization/project authorization, including project-scoped API keys. Host history/settings require a platform administrator; API keys cannot change retention or inspect host history. Responses include only selected telemetry/log fields, never Docker environment variables or config labels. Quota views show recent measured CPU/RAM separately from reserved allocation; partial/stale measurements stay explicit.

API: `GET /api/v1/services/{id}/history?from=<RFC3339>&to=<RFC3339>`, `GET /api/v1/services/{id}/logs/history?from=…&to=…&q=…&before=<cursor>`, `GET /api/v1/monitoring/history?from=…&to=…`, and admin-only `GET/POST /api/v1/monitoring/settings`. Query ranges are limited to 31 days. Search is a bounded case-insensitive literal substring, with no SQL or regular-expression interpolation.
