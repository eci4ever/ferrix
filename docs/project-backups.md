# Coordinated project backup and restore

Open **Project backups** below the service cards. **Create encrypted backup** requires explicit downtime consent. Close Ferrix terminals and pause external database clients, scheduled database writers and other processes first. Ferrix locks project configuration/lifecycle changes, stops every managed Application/worker, captures PostgreSQL/MariaDB logical backups and persistent Application volumes, then restores each original writer's running/stopped state and restart policy. Databases stay running for their logical dump tools. The consistency boundary is the project's managed writers plus the external writers the operator paused; this is not a distributed transaction across unrelated live systems.

The versioned manifest ties service/runtime settings, environment values, environment networks, immutable image/source references, custom-domain references and archive checksums together. Application archives preserve numeric UID/GID, file modes and timestamps under the per-volume backup rules; symlinks, special files, ACLs and extended attributes are unsupported. Project bundles support 1–20 successfully deployed services, PostgreSQL/MariaDB and Applications. Other database engines are rejected before downtime.

Portable exports are limited to **64 MiB total**. Use the existing per-service local/S3 backups for larger data sets. The bundle contains image references, not image layers: the exact immutable image IDs must already exist on the destination Docker daemon. The import preview reports missing images before creating containers. Transfer original images with your registry or an operator-controlled Docker save/load process; Ferrix never silently substitutes a mutable tag or rebuilds a newer source revision.

## Recovery key

Each export uses a fresh random 256-bit recovery key and authenticated XChaCha20-Poly1305 encryption. The key is shown once. Store it in a password manager separately from the downloaded `.enc` file, verify the download and keep an independent copy. The API wraps the temporary job key using the installation key while working, then removes it after completion/recovery. Losing the separate recovery key makes the export unusable through Ferrix. Database/WAL backups and the installation authentication key remain sensitive and need normal secure storage.

Application environment secrets are included inside the encrypted manifest. Installation users, sessions, API keys, MFA state, `FERRIX_AUTH_KEY`, operator environment and account-wide Cloudflare/S3 credentials are not exported. GitHub provider tokens, webhooks, auto-deploy and backup schedules/destinations are not copied. Imported application/database secrets are re-encrypted with fresh target-service associated data under the destination installation key. Export/import/download and cutover require an organization manager browser session; these endpoints are not enabled for API keys.

The latest five encrypted exports per source project and five pending import previews per originating project are retained. Completed imports discard their uploaded encrypted payload after restore; failed imports discard their temporary key/payload. Temporary per-service dump files used by project operations enter the existing owned-file retention cleanup queue after packaging/restoring. Cleanup waits for pending readers and retries on failure; it never prunes images, unrelated backups, live volumes or other projects. Metadata/checksums remain available in history after payload pruning.

## Isolated restore and cutover

Upload the encrypted bundle with its recovery key and review service mappings and missing images. **Restore to new isolated project** creates new project/environment/service IDs and new volumes. Internal `ferrix-<service-id>` references in environment values are rewritten to the new service aliases. Review other application-specific external URLs and credentials before activation; Ferrix does not guess arbitrary connection-string semantics.

All restored Applications are initially stopped. Databases run privately so their data can be restored and inspected. Public routing stays disabled. Once restore completes, web Applications can be started for server-only loopback validation. Restored workers remain protected from Start/Reload/Deploy until project cutover. Verify files, UID/GID, database rows and application behavior before continuing.

**Cut over** requires another explicit confirmation. On the same installation, Ferrix freezes the owned source/target projects, stops the original project's managed Application writers, checks target startup/health and activates restored services that were running in the backup. It commits public traffic and any owned custom-domain transfers atomically. Automatic hostnames use the new service IDs. Custom-domain references only move when the current source mapping still belongs to the same owned source project; unrelated project routes are untouched. Conflicting target mappings can prevent cutover; review Domains and retry. On another installation, the operator must stop the external original writers first and configure/verify destination DNS/domain ownership. Origin IDs alone never grant access to another organization.

Source/restore lineage locks prevent legitimate related writer instances from starting simultaneously on the same Docker host. During interrupted/failed cutover, target writers/traffic are stopped before source recovery. Interrupted backups recover recorded original writer states; a parent job stays in recovery while shutdown/helper state is uncertain. Docker administrators and external installations remain outside these application-level locks.

A partial restore never overwrites the source. It leaves the new target isolated and incomplete services blocked. Inspect its progress, delete failed target services/data through the normal confirmed deletion flow, and import again into a fresh project. Do not manually start a failed target. The project backup history identifies the isolated target and progress; normal retained monitoring can correlate deployment/restart events.
